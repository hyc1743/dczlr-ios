# ARM64 原生执行与 Metal 宿主

## 已确认的目标

最终应用运行游戏自身的 AArch64 代码。苹果平台宿主提供游戏需要的系统服务、文件、
线程、音频、输入和图形接口；图形接口直接调用 Metal。原版着色器在构建前离线转换，
设备上加载转换后的产物。运行时不使用 CPU 解释器、动态二进制翻译、Wine、DXVK
或 MoltenVK。此前的无 JIT 解释器 IPA 属于另一项实验，不满足这个架构目标。

```text
构建前：游戏源码或经验证的离线重建 → AArch64 游戏代码
        原版着色器和 effect → 离线语义转换 → Metal shader 库及绑定清单

设备上：已签名的 AArch64 游戏代码
          ├─ 系统与 ABI 适配 → 苹果平台线程、同步、时间和内存服务
          ├─ 文件接口 → 用户导入的数据与独立存档
          ├─ 音频、输入 → 苹果平台音频及触控／手柄接口
          └─ 原生图形适配 → Metal → 屏幕
```

这是目标架构，不是已经实现的执行链。

## 当前输入与参考项目的区别

2026-10-23 对当前项目根目录的可执行候选文件做了静态 PE 检查：主程序、附带 DLL
和注册表辅助程序均为 `Machine=0x014c` 的 PE32 x86。主程序 SHA-256 为
`70aebdcde6bd8c252e45db14086fb4ac8837da8dd66c267c05ec7f470f5f9b07`，
与先前记录一致。没有执行这些文件。这次检查仅覆盖根目录的相应文件，
不声称已经搜索所有目录或资源容器，也没有发现本游戏已有 ARM64 版本的证据。

参考项目 `weixing3` 的输入则是已有的 ARM64 NRO，其准备工具保留并改写原有代码，
宿主负责启动、重定位与平台接口。它不能作为把当前 x86 主程序变成 AArch64 的工具。

参考项目的 `ios/runtime/Biko3Vulkan.c` 和 `docs/graphics-bridge.md` 明确使用
Vulkan 调用到 MoltenVK 的桥接。因此可以研究它的宿主边界、静态 hook、文件、输入
和音频组织方式；本方案的直接 Metal 后端需要独立实现。

已有着色器证据来自 `research/rea-pe-resources.json` 的 REA
`inspect_pe_resources` 记录（Evidence
`ev_f314ea821e89062aab3a5e0c7b92dafc8d26311ca5bf4d4ac2335a728c7231f4`）。
该记录只确认资源范围与哈希，不是 effect 或 shader 语义转换成功的证据。
修正后的 token 分帧器也不能代替完整转换器。

## 首个必需条件：得到游戏的 AArch64 代码

可研究的输入路径是已有的 ARM64 程序、源码重编译，或从现有 x86 程序离线恢复与
重建后再编译。当前没有前两种输入的证据，第三种路径是否能覆盖完整游戏尚未证明。
必须先评估这一点；增加宿主 API 或转换着色器不能弥补缺失的 ARM64 游戏逻辑。

离线重建至少需要处理间接跳转与回调、32 位指针和数据布局、调用约定、异常与展开、
TLS、浮点语义、动态导入，以及代码与数据的区分。如果无法恢复关键路径，应记录
失败范围，不能以运行时 x86 解释器补齐后仍称为本方案。

即便获得 AArch64 输入，也要核对其 ABI、平台专用指令、TLS、重定位与展开信息。
最终代码应在构建阶段进入可签名的应用可执行映像，宿主运行时仅设置所需数据和
适配入口；同为 AArch64 并不代表任意平台二进制可直接作为 iOS 程序加载。

## 实现顺序与验收

1. **原生代码可行性。** 找到可用 ARM64 输入，或为离线重建建立有证据的控制流、
   函数、导入与 ABI 清单。先验证一条来自原程序的可辨认逻辑路径；自制测试只能
   验证工具，不能当作游戏代码已移植。
2. **启动与平台服务。** 明确启动契约及实际需要的系统服务，以原生函数实现适配。
   未实现接口必须明确失败，不能无条件返回成功。存档与配置不能被资源恢复覆盖。
3. **离线着色器转换。** 恢复实际使用的 effect、technique、pass、shader、常量和
   采样器绑定；保留原始哈希、入口、转换工具版本与状态描述。构建 Metal shader
   库；运行时不再解析原版 shader 字节码。未知格式和指令应停止转换。
4. **直接 Metal 图形接口。** 根据已恢复的调用实现所需 D3D9／D3DX9 语义，包括
   资源、布局、渲染状态、深度／混合、渲染目标与提交。使用离线生成的 shader 库
   创建 Metal pipeline；这不等于消除驱动内部的 pipeline 编译。
5. **实机整合。** 分别记录原生游戏入口、原始逻辑、首帧、输入、实际声音、存档、
   前后台恢复及完整可玩性。构建成功或宿主三角形不构成游戏移植成功。

“小型宿主”是尽量只覆盖所需接口的设计目标。目前没有足够的调用覆盖证据估算其
规模，也没有完整 ARM64 游戏代码或直接 Metal 游戏渲染器。

## 与此前实验的关系

保留解释器源码、构建和测试记录，供独立研究使用。它们不再作为本路线的交付目标，
也不要求用户先完成 Wine 的手机测试。后续推进重点是原生代码可行性及离线转换证据，
而不是继续完善解释器宿主。
